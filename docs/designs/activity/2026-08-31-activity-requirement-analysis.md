# 活动发布与报名需求分析方案

## 1. 文档目的

本文档用于规划 BlissTribe 的“活动发布与报名”能力，重点回答三个问题：

- 后台如何发布和管理活动。
- 小程序用户如何发现活动、查看详情并报名。
- 活动如何和现有产品、标签、评估、线索、B 端伙伴体系协同。

本阶段目标不是做完整活动营销平台，而是在现有产品推荐和线索闭环基础上，补一个可运营、可验收、后续可扩展的活动模块。

## 2. 当前系统基础

当前项目已经具备以下能力：

```text
后台维护产品模块、标签、评估、产品、推荐规则
  ↓
小程序展示模块、评估、推荐产品
  ↓
用户提交咨询线索
  ↓
后台查看线索、跟进、查看推荐分析
```

活动模块可以复用现有基础：

| 现有能力 | 活动可复用方式 |
| --- | --- |
| 标签字典 | 活动可绑定标签，用于推荐、筛选、画像沉淀 |
| 产品模块 | 活动可归属到业务模块，如健康、成长、社群 |
| 用户登录 | 报名前需要登录，避免匿名报名无法跟进 |
| 推荐事件 | 活动曝光、点击、报名可以沉淀行为数据 |
| 线索跟进思想 | 活动报名后进入报名管理和跟进状态 |
| B 端邀请来源 | 活动报名可记录邀请来源，后续支持 B 端推广 |

## 3. 需求背景

活动和产品的业务属性不同。

产品通常是长期供给，强调“适合谁、解决什么问题、怎么咨询或购买”。活动通常有明确时间、名额、地点或参与方式，强调“什么时候参加、是否可报名、报名后如何通知和跟进”。

因此不建议把活动简单作为 `Product.productType = event` 塞入产品表。短期看会省表，长期会让产品字段和活动字段混在一起，例如活动时间、报名截止、名额、签到、活动状态、报名状态都不是产品天然属性。

推荐方案：

```text
活动独立建模：Activity
活动报名独立建模：ActivityRegistration
活动可关联产品：activity.relatedProductIds
活动可使用标签：tagIds/tags
活动行为复用 RecommendationEvent 或后续扩展为统一 BehaviorEvent
```

这样可以保持职责清晰，也方便后续活动运营、报名管理、签到、通知、复盘统计。

## 4. 目标用户与场景

### 4.1 C 端用户

C 端用户在小程序中可以：

- 在首页看到推荐活动。
- 在活动列表按模块、活动状态、活动类型筛选。
- 查看活动详情。
- 登录后报名活动。
- 查看我的报名记录。
- 取消报名或补充报名信息，具体是否允许由活动配置决定。

### 4.2 后台运营人员

后台运营可以：

- 创建和编辑活动。
- 设置活动状态、时间、报名截止、名额、地点、封面、详情。
- 选择活动归属模块和标签。
- 关联推荐产品。
- 查看报名列表。
- 修改报名状态和跟进备注。
- 查看活动曝光、点击、报名转化。

### 4.3 B 端伙伴

第一阶段不做完整 B 端活动工作台，但要预留来源记录：

- B 端可分享活动链接。
- C 端通过邀请链接报名时，记录 `partnerId` 或 `sourceInviteCode`。
- 后台能看到报名来源。

后续再开放 B 端查看自己带来的活动报名。

## 5. 方案比较

### 5.1 方案 A：把活动作为产品类型

实现方式：

```text
Product.productType 增加 event
报名复用 ProductLead
活动字段塞入 Product 扩展字段
```

优点：

- 改动少。
- 可以快速复用产品列表、详情和线索。
- 短期演示快。

缺点：

- 产品和活动职责混乱。
- 活动时间、名额、报名截止、签到等字段会污染产品模型。
- 后台维护体验不清晰。
- 后续做活动报名统计、活动状态流转会变复杂。

适用场景：

- 只有极少量活动。
- 活动只是“活动类产品”的简单展示，不需要报名管理。

### 5.2 方案 B：活动独立建模，报名独立管理

实现方式：

```text
新增 Activity
新增 ActivityRegistration
活动可关联 Product
活动可绑定 ProductModule 和 TagDictionary
```

优点：

- 业务边界清晰。
- 小程序活动体验更自然。
- 后台可以独立管理活动和报名。
- 后续支持签到、通知、名额、候补、复盘统计更顺。

缺点：

- 需要新增表、接口、后台页面和小程序页面。
- 第一版工作量比方案 A 大。

适用场景：

- 活动会持续运营。
- 活动需要报名、名额、时间和跟进。
- 后续希望活动带动产品咨询或 B 端推广。

### 5.3 方案 C：活动作为内容 CMS

实现方式：

```text
新增内容表 Content
contentType = activity
报名跳转产品或外部表单
```

优点：

- 内容发布灵活。
- 适合文章、活动、专题混合展示。

缺点：

- 报名能力弱。
- 后台难以做活动报名状态管理。
- 数据闭环不如独立活动模型清晰。

适用场景：

- 主要做内容发布，不强调报名跟进。

## 6. 推荐方案

推荐采用方案 B：活动独立建模，报名独立管理。

原因：

- 符合当前业务的“活动可报名、报名后跟进”诉求。
- 不破坏现有产品模型。
- 可以和产品推荐体系协同，但不和产品职责混在一起。
- 后续可以平滑扩展签到、候补、通知、活动复盘。

第一版活动模块建议控制范围：

```text
后台发布活动
小程序查看活动
用户登录后报名
后台查看报名并跟进
活动基础数据统计
```

暂不做：

- 在线支付。
- 活动签到核销。
- 复杂候补队列。
- 群发通知。
- 活动分销结算。
- 活动 AI 推荐。

## 7. 核心业务流程

### 7.1 后台发布活动

```text
运营创建活动
  ↓
填写基础信息、时间、报名规则、名额、地点/方式
  ↓
选择模块和标签
  ↓
可选关联产品
  ↓
保存草稿
  ↓
发布活动
  ↓
小程序可见
```

### 7.2 小程序报名活动

```text
用户进入首页或活动列表
  ↓
查看活动卡片
  ↓
进入活动详情
  ↓
点击报名
  ↓
未登录则先登录
  ↓
填写报名信息
  ↓
提交报名
  ↓
生成 ActivityRegistration
  ↓
用户可在“我的活动”查看报名状态
```

### 7.3 后台跟进报名

```text
运营查看报名列表
  ↓
筛选新报名/已确认/已取消/已参加
  ↓
查看用户信息和报名备注
  ↓
更新报名状态
  ↓
记录跟进备注
```

### 7.4 活动带动产品咨询

活动详情页可展示关联产品：

```text
活动详情
  ↓
相关产品推荐
  ↓
用户点击产品
  ↓
提交产品咨询
  ↓
ProductLead.sourceScene = activity_detail
metadata 记录 activityId
```

这样活动既能独立报名，也能导流到产品线索。

## 8. 小程序页面设计建议

### 8.1 首页

首页增加“近期活动”区域。

展示规则：

- 最多展示 2-3 个活动。
- 优先展示已发布、报名中、未结束的活动。
- 显示活动标题、封面、时间、地点/方式、报名状态。
- 提供“全部活动”入口。

不建议首页展示太多活动，避免冲淡产品推荐主线。

### 8.2 活动列表页

新增页面：

```text
pages/activities/index
```

能力：

- 展示活动列表。
- 支持模块筛选。
- 支持状态筛选：报名中、即将开始、已结束。
- 支持活动类型筛选：线上、线下、混合。

卡片字段：

| 字段 | 展示方式 |
| --- | --- |
| 封面 | 顶部图片 |
| 标题 | 主标题 |
| 副标题 | 简短说明 |
| 时间 | 活动开始时间 |
| 方式 | 线上/线下/混合 |
| 名额 | 剩余名额或不限名额 |
| 状态 | 报名中/已满/已结束 |

### 8.3 活动详情页

新增页面：

```text
pages/activities/detail
```

内容结构：

- 活动封面。
- 活动标题和副标题。
- 活动时间。
- 报名截止时间。
- 活动方式和地点。
- 适合人群。
- 活动亮点。
- 活动详情。
- 关联产品。
- 底部固定报名按钮。

报名按钮状态：

| 状态 | 按钮 |
| --- | --- |
| 未开始报名 | 暂未开始 |
| 报名中 | 立即报名 |
| 已报名 | 已报名，查看记录 |
| 名额已满 | 名额已满 |
| 已截止 | 报名已截止 |
| 已结束 | 活动已结束 |

### 8.4 我的活动

新增页面：

```text
pages/profile/activity-registrations
```

用于展示用户报名记录：

- 活动标题。
- 活动时间。
- 报名状态。
- 报名备注。
- 查看详情入口。

个人中心可增加“我的活动”入口。

## 9. 后台管理设计建议

### 9.1 菜单结构

建议后台新增一级菜单或产品运营下的二级菜单：

```text
运营管理
  - 活动管理
  - 活动报名
```

如果保持当前产品运营菜单，也可以放在：

```text
产品运营
  - 产品管理
  - 模块管理
  - 标签管理
  - 评估管理
  - 推荐规则
  - 线索跟进
  - 活动管理
  - 活动报名
```

短期建议放在产品运营下，减少菜单重构成本。

### 9.2 活动管理页

列表能力：

- 按状态筛选。
- 按模块筛选。
- 按活动类型筛选。
- 搜索活动标题。
- 查看报名人数、名额、报名转化。
- 发布、下线、编辑。

编辑字段：

| 字段 | 是否必填 | 说明 |
| --- | --- | --- |
| moduleId | 是 | 归属模块 |
| title | 是 | 活动标题 |
| subtitle | 否 | 活动副标题 |
| coverUrl | 否 | 活动封面 |
| activityType | 是 | online/offline/mixed |
| startAt | 是 | 开始时间 |
| endAt | 是 | 结束时间 |
| registrationStartAt | 否 | 报名开始时间 |
| registrationEndAt | 是 | 报名截止时间 |
| locationText | 否 | 地点或线上参与方式 |
| capacity | 否 | 名额，空值代表不限 |
| targetUserText | 否 | 适合人群 |
| highlights | 否 | 活动亮点 |
| detail | 否 | 活动详情 |
| tags/tagIds | 否 | 活动标签 |
| relatedProductIds | 否 | 关联产品 |
| status | 是 | 草稿/发布/下线 |
| sortOrder | 否 | 排序 |

### 9.3 活动报名页

列表能力：

- 按活动筛选。
- 按报名状态筛选。
- 搜索用户昵称、手机号、报名备注。
- 查看报名时间。
- 修改报名状态。
- 记录跟进备注。

报名状态建议：

| 状态 | 说明 |
| --- | --- |
| registered | 已报名 |
| confirmed | 已确认 |
| attended | 已参加 |
| cancelled | 已取消 |
| no_show | 未到场 |
| invalid | 无效报名 |

第一版可以只用 `registered/confirmed/cancelled/attended`。

## 10. 数据模型建议

### 10.1 Activity

建议字段：

```text
id
moduleId
title
subtitle
coverUrl
activityType        online/offline/mixed
startAt
endAt
registrationStartAt
registrationEndAt
locationText
capacity            null 表示不限名额
registeredCount     可冗余，也可实时 count
targetUserText
highlights          String[] 或 Json
detail
tags
tagIds
relatedProductIds
priority
sortOrder
status              0草稿 1发布 2下线
publishedAt
createdAt
updatedAt
deletedAt
```

设计说明：

- `moduleId` 让活动归属于健康、成长、社群等模块。
- `tagIds/tags` 和产品推荐保持同一套标签语言。
- `relatedProductIds` 第一版可用数组，后续如果需要排序、主推关系，再拆 `ActivityProduct` 关联表。
- `registeredCount` 第一版可以实时统计，避免报名取消后计数一致性问题。若性能有压力再冗余。

### 10.2 ActivityRegistration

建议字段：

```text
id
activityId
userId
partnerId
sourceInviteCode
sourceScene
name
phoneMasked
message
status
followUpNote
cancelReason
createdAt
updatedAt
```

设计说明：

- `activityId + userId` 建议加唯一约束，避免同一用户重复报名同一活动。
- `partnerId/sourceInviteCode` 支持 B 端推广来源。
- `phoneMasked` 可用于后台展示，不保存明文手机号。
- 报名详情如果以后变复杂，再扩展 `formData Json`。

### 10.3 ActivityRegistrationFollowUp

第一版可选。

如果希望和产品线索一致，建议新增：

```text
id
registrationId
operatorId
operatorType
fromStatus
toStatus
note
createdAt
```

如果第一版只需要简单报名管理，也可以先只保留 `followUpNote`。

推荐第一版先不加 follow-up 表，等活动跟进确实复杂后再加。

查询参数：

## 12. 活动推荐与产品推荐关系

活动可以出现在三个位置：

```text
首页近期活动
模块页活动推荐
评估结果页相关活动
```

第一版推荐规则：

```text
已发布
未结束
当前可报名优先
模块匹配优先
标签匹配优先
priority 高优先
sortOrder 小优先
startAt 近优先
```

活动不应该替代产品推荐。活动更适合承担：

- 拉新。
- 内容教育。
- 社群互动。
- 为产品咨询预热。
- 收集需求。

产品更适合承担：

- 服务咨询。
- 实物购买。
- 组合方案转化。

## 13. 数据闭环

活动需要记录以下行为：

| 行为 | 说明 |
| --- | --- |
| impression | 活动卡片曝光 |
| click | 点击活动 |
| registration_submit | 提交报名 |
| cancel | 取消报名 |

短期可以复用 `RecommendationEvent`，但需要注意 `productId` 可为空、`metadata.activityId` 记录活动 ID。

更长期建议演进为统一行为事件表：

```text
BehaviorEvent
  targetType = product/activity/module/assessment
  targetId
  eventType
  sourceScene
  userId/anonymousId
  tagIds/tags
  metadata
```

第一版不建议立刻迁移事件模型，避免牵动现有推荐分析。

## 14. 权限与规则

### 14.1 报名必须登录

活动报名建议必须登录。

原因：

- 报名后需要查看报名记录。
- 后台需要识别用户和联系方式。
- 后续可以和标签画像、B 端来源、活动转化关联。

未登录时流程：

```text
点击报名
  ↓
弹出登录授权
  ↓
登录成功
  ↓
回到活动报名确认
  ↓
提交报名
```

### 14.2 重复报名

同一用户同一活动只允许一条有效报名。

规则：

- 已报名、已确认、已参加：不可重复报名。
- 已取消：可重新报名，或恢复原报名，第一版建议恢复原报名。
- 无效报名：后台标记后是否允许重新报名，第一版建议允许。

### 14.3 名额限制

第一版可以用实时计数控制：

```text
有效报名数 < capacity
```

有效状态：

```text
registered
confirmed
attended
```

并发风险：

- 如果活动名额很小，可能出现同时报名超额。
- 第一版可接受低风险。
- 如果真实活动名额敏感，再使用数据库事务和行锁控制。

## 15. 分阶段实施建议

### 阶段 1：MVP 活动报名闭环

目标：

```text
后台能发活动
小程序能展示活动
用户能报名
后台能看报名
```

实现内容：

- 新增 `Activity`、`ActivityRegistration`。
- 新增后台活动管理页。
- 新增后台报名管理页。
- 新增小程序活动列表页、详情页、我的活动页。
- 首页展示近期活动。
- `pnpm check:local` 增加活动接口冒烟检查。

验收标准：

- 后台可创建草稿活动。
- 发布后小程序可见。
- 未登录点击报名会先登录。
- 登录后可报名。
- 重复报名被拦截。
- 报名后后台可见。
- 活动名额满后不可继续报名。

### 阶段 2：活动与产品转化联动

目标：

```text
活动为产品咨询导流
```

实现内容：

- 活动关联产品。
- 活动详情展示相关产品。
- 从活动进入产品详情时记录 `sourceScene = activity_detail`。
- 产品线索 metadata 记录 activityId。
- 后台活动详情展示关联产品咨询数。

验收标准：

- 活动详情可看到关联产品。
- 点击关联产品可进入产品详情。
- 从活动产生的产品咨询可追溯到活动。

### 阶段 3：活动数据分析

目标：

```text
运营知道活动有没有效果
```

实现内容：

- 活动曝光、点击、报名事件。
- 后台活动列表展示曝光、点击、报名、报名率。
- 活动详情展示报名用户画像和标签分布。

验收标准：

- 后台可以看到每个活动的报名人数。
- 可以看到活动报名率。
- 可以看到不同模块、标签活动的效果。

### 阶段 4：通知、签到和候补

目标：

```text
支持更完整的活动履约
```

实现内容：

- 活动开始前提醒。
- 报名成功通知。
- 签到码或核销。
- 名额满后候补。
- 未到场状态。

该阶段建议在真实活动运营后再启动。

## 16. 小程序信息架构建议

活动入口建议：

```text
首页
  - 近期活动
  - 查看全部

产品/模块页
  - 模块相关活动

个人中心
  - 我的活动
```

不建议活动成为底部 Tab 的第一版入口。当前业务核心仍是产品推荐和咨询线索，活动应作为运营触点嵌入首页和模块页。

## 17. 后台信息架构建议

当前后台菜单建议新增：

```text
产品运营
  - 活动管理
  - 活动报名
```

如果后续活动成为高频运营动作，再抽成：

```text
运营中心
  - 活动管理
  - 活动报名
  - 内容专题
  - 运营看板
```

第一版不建议重构后台菜单，避免范围扩大。

## 18. 风险与处理

| 风险 | 表现 | 建议 |
| --- | --- | --- |
| 活动和产品边界混乱 | 活动字段塞进产品表 | 活动独立建模，产品只做关联 |
| 报名数据不可跟进 | 只记录人数，不记录用户 | 使用 `ActivityRegistration` 记录用户报名 |
| 未登录报名丢失 | 用户填写后登录，报名信息没保存 | 报名前先要求登录，或本地缓存报名草稿 |
| 名额超卖 | 同时多人报名 | 第一版可事务校验，名额敏感时加锁 |
| 后台菜单变复杂 | 产品/活动/线索混杂 | 第一版放产品运营下，后续再拆运营中心 |
| 事件模型重复 | 活动也要曝光点击 | 第一版用 metadata 过渡，后续统一 BehaviorEvent |

## 19. 工程原则评估

### KISS

第一版只做发布、展示、报名、报名管理，不做支付、签到、候补、通知和自动营销，保证功能简单可验收。

### YAGNI

不提前做完整活动营销平台，不提前拆复杂关联表，不提前建设统一事件平台。等活动真实运营后再按数据演进。

### SOLID

`Activity` 负责活动信息，`ActivityRegistration` 负责报名状态，`Product` 继续负责产品供给，`ProductLead` 继续负责产品咨询线索。模块职责清晰。

### DRY

活动复用已有标签、模块、用户、B 端来源、行为事件口径，不在小程序维护静态活动配置。

## 20. 推荐落地顺序

建议按以下顺序实现：

```text
1. 数据模型和迁移：Activity / ActivityRegistration
2. API：公开活动、报名、我的报名、后台活动、后台报名
3. 后台：活动管理、报名管理
4. 小程序：首页近期活动、活动列表、活动详情、我的活动
5. 验收脚本：加入活动接口冒烟检查
6. 种子数据：构造 3-5 个活动用于本地验收
```

第一阶段完成后，再评估是否进入“活动关联产品转化”和“活动数据分析”。
