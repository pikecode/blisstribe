# 推荐评分增强设计

## 1. 背景

当前推荐链路已经完成标签 ID 化：产品、评估选项、推荐规则、用户评估和线索都可以保存标签 ID，并保留标签名称作为展示快照。下一步不建议继续堆大量手工规则，而是让产品和评估本身表达推荐权重。

本阶段目标是让推荐从“是否命中标签”升级为“命中哪些标签、强度是多少、产品是否强相关”。

## 2. 推荐方案

采用三层推荐体系：

1. 自动匹配：基于用户评估标签和产品推荐配置计算基础分。
2. 运营规则：少量关键场景手工加分和自定义推荐理由。
3. 兜底策略：标签不足或无命中时按产品优先级、排序和发布时间展示。

当前实施第一层增强，保留第二层已有能力。

## 3. 数据设计

评估选项新增：

| 字段 | 说明 |
| --- | --- |
| `tagWeights Json` | 选项产出标签的强度，key 为标签 ID，value 为权重 |

产品新增：

| 字段 | 说明 |
| --- | --- |
| `primaryTagIds BigInt[]` | 强相关标签，命中后加较高分 |
| `secondaryTagIds BigInt[]` | 弱相关标签，命中后加较低分 |
| `excludeTagIds BigInt[]` | 排除标签，命中后产品不进入推荐结果 |

继续保留：

| 字段 | 说明 |
| --- | --- |
| `Product.tagIds` | 产品全部推荐标签，兼容旧逻辑和列表展示 |
| `AssessmentOption.tagIds` | 选项产出标签 ID |
| `tags` 字符串数组 | 展示快照和历史兼容 |

## 4. 评分逻辑

推荐基础分：

```text
基础分 =
产品优先级
+ 强相关标签命中权重分
+ 弱相关标签命中权重分
+ 普通标签命中兜底分
+ 运营规则加分
```

默认权重：

| 类型 | 分值 |
| --- | --- |
| 强相关标签 | 用户标签权重 * 20 |
| 弱相关标签 | 用户标签权重 * 10 |
| 普通标签 | 用户标签权重 * 5 |
| 旧名称命中 | 10 |

评估选项未配置权重时，默认该选项的标签权重为 1。

排除规则：

1. 用户标签命中产品 `excludeTagIds` 时，产品不进入自动推荐结果。
2. 排除标签用于明显不适合的产品场景，例如用户选择 `暂不联系` 时，不推荐强咨询型产品。

## 5. 管理端维护方式

产品管理：

1. `推荐标签` 表示产品整体适配范围。
2. `强相关标签` 表示产品最应该命中的核心需求。
3. `弱相关标签` 表示产品可以覆盖但不是主场景的需求。
4. `排除标签` 表示用户出现这些需求时不推荐该产品。

评估模板：

1. 选项仍然选择标签。
2. 每个已选标签可以配置权重。
3. 不配置时默认权重为 1。

推荐规则：

1. 继续作为运营增强工具。
2. 不建议每个产品都配规则。
3. 只用于重点产品、活动产品或特殊组合标签。

## 6. 兼容策略

1. 小程序继续展示标签名称，不需要立即改 UI。
2. 小程序远程评估模板会收到 `tagWeights`，提交评估时同步权重快照。
3. 本地兜底评估没有权重时，后端按默认权重 1 处理。
4. 旧产品没有强弱标签配置时，系统把 `tagIds` 作为普通标签参与兜底评分。

## 7. 验收标准

1. 后台产品编辑可以维护强相关、弱相关、排除标签。
2. 后台评估模板选项可以维护每个标签的权重。
3. 小程序提交评估后，用户评估保存标签 ID 和权重快照。
4. 推荐接口按强弱标签计算分数。
5. 命中排除标签的产品不会出现在推荐列表。
6. 手工推荐规则仍能额外加分和覆盖推荐理由。

## 8. 工程原则

KISS：使用数组和 JSON 字段实现评分增强，不引入推荐引擎。

YAGNI：暂不做机器学习、用户画像合并、复杂规则表达式。

SOLID：标签归一、评分计算、运营规则分别承担不同职责。

DRY：后台所有标签选择继续复用统一分组选择工具。
