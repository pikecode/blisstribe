# 商城第一阶段闭环完善设计

**日期：** 2026-09-23  
**状态：** 开始实施  
**范围：** 平台自营、单订单、实物商品、微信小程序用户、平台管理员

## 目标

将现有商城实现收敛到优化版设计的第一阶段：商品浏览、购物车、服务端定价下单、库存预留、支付入口、订单管理、手工发货、整单退款。优先保证金额、库存、归属校验和外部支付失败时的数据正确性。

## 设计决策

1. 保留 NestJS + Prisma + PostgreSQL 模块化单体，不拆微服务。
2. 继续使用整型分为金额单位；客户端只提交商品 ID、数量和收货信息，价格、优惠及支付金额以服务端计算为准。
3. 商品库存以 PostgreSQL 为事实来源。下单通过带库存条件的原子更新预留；取消和过期通过订单状态条件更新保证只释放一次。
4. 第一阶段仅接受整单退款。退款请求、审核和回调按状态及订单剩余可退款金额约束；外部微信调用不放在数据库事务中。
5. 微信支付 V3 尚未具备可验证的商户配置时必须失败关闭：不能生成伪预支付参数、不能接受未验签通知、不能伪造退款成功。真实凭据与平台证书配置属于上线前置条件。
6. 管理端复用 `AdminJwtGuard`，审核人 ID 来自认证上下文；消费者订单及退款查询均按认证用户过滤。
7. 小程序复用现有视觉规范，不新增商城主导航或运营功能；修复真实流程所需的结算页、支付状态刷新、订单字段映射和退款入口。

## 关键数据流

```text
商品/分类
  -> 购物车（不预留库存）
  -> 下单事务（读取当前商品数据、原子预留库存、写金额与商品快照）
  -> 服务端发起支付（只允许订单所有者操作）
  -> 验签解密后的微信通知（幂等更新支付/订单/库存）
  -> 管理员发货
  -> 用户申请整单退款
  -> 管理员审核、微信退款通知幂等完成
```

所有支付与退款网络请求均在数据库事务之外执行。订单状态和支付/履约/退款状态字段需保持一致，失败或未知结果保留可重试状态，不通过定时任务猜测并修改财务或库存事实。

## 错误处理与安全约束

- 非法商品状态、数量、价格/库存边界和不完整收货信息在服务端拒绝。
- 无权限访问统一返回不可枚举式错误；外部回调只有签名和资源解密成功后才进入业务服务。
- 外部支付结果未知时保留处理中状态并等待回调或主动对账；对账仅报告差异，不自动重复修改库存。
- 退款累计金额永不超过成功支付金额；重复请求、重复回调和并发审核不能重复退款或释放/扣减库存。
- 生产环境若未显式配置正式支付适配器与必要密钥，支付和退款必须不可用。

## 验收标准

- 创建订单的订单项字段与 Prisma schema 一致，商品名称、图片、单价和小计均为下单快照。
- 并发下单不能超卖；取消、过期、支付和退款回调可重复执行而不重复变更库存。
- 订单支付接口只允许订单所有者发起；管理员写接口使用真实管理员身份。
- 模拟/未配置支付环境不可能返回成功支付参数或通过验签。
- 小程序结算路由存在且注册；商品、订单和退款的字段与 API 一致，页面不再展示开发中的假成功状态。
- API 定向测试、类型检查和 Admin/小程序构建通过；支付上线仍需微信商户沙箱凭据与回调联调。

## 工程原则

- **KISS / YAGNI：** 第一阶段仍限单店、单价格、实物履约，不实现 SKU、分账、优惠或虚拟预约。
- **SOLID：** 支付渠道封装在适配器内；订单、库存、退款规则由后端服务承担，控制器只负责认证上下文和 DTO。
- **DRY：** 统一金额/状态契约，避免 miniapp 与 admin 各自维护不兼容订单模型。

## 实施路线

1. 修复订单创建、库存并发和支付/退款接口安全底座。
2. 修复订单状态机、取消/过期释放、退款幂等和只报告型对账。
3. 统一商品/订单/退款 API 契约，补全小程序结算和页面状态。
4. 补充并运行聚焦测试、类型检查和构建，整理微信支付上线前置清单。
