# 标签 ID 化迁移设计

## 1. 背景

当前系统已经有 `TagDictionary` 标签字典，但产品、评估选项、推荐规则、用户评估和线索仍主要保存标签名称数组。这个方案实现简单，但长期会有两个问题：

1. 标签改名会影响匹配稳定性。
2. 同名标签跨模块扩展后，单靠名称难以表达准确含义。

因此本阶段采用方案 B：把推荐链路升级为标签 ID 优先，同时保留名称快照兼容现有小程序和历史数据。

## 2. 目标

本阶段实现以下能力：

1. 产品保存 `tagIds`，`tags` 作为展示快照。
2. 评估选项保存 `tagIds`，`tags` 作为展示快照。
3. 推荐规则保存 `conditionTagIds`，`conditionTags` 作为展示快照。
4. 用户评估保存 `tagIds`，`tags` 作为展示快照。
5. 产品线索保存 `needTagIds`，`needTags` 作为展示快照。
6. 推荐匹配优先使用 ID，旧数据或兜底模板继续使用名称匹配。

## 3. 非目标

本阶段暂不做以下内容：

1. 不删除旧的 `tags`、`conditionTags`、`needTags` 字段。
2. 不引入复杂标签权重、别名、排除条件。
3. 不把用户基础资料标签改为 ID。
4. 不做后台批量标签迁移工具，先通过数据库迁移和保存时归一化覆盖主要场景。

## 4. 数据设计

新增字段：

| 表 | 新字段 | 说明 |
| --- | --- | --- |
| `Product` | `tagIds BigInt[]` | 产品推荐标签 ID |
| `AssessmentOption` | `tagIds BigInt[]` | 评估选项产出的标签 ID |
| `AssessmentRecommendationRule` | `conditionTagIds BigInt[]` | 推荐规则命中条件标签 ID |
| `UserAssessment` | `tagIds BigInt[]` | 用户本次评估产生的标签 ID |
| `ProductLead` | `needTagIds BigInt[]` | 线索需求标签 ID |

保留名称数组字段作为快照，原因是：

1. 小程序仍要展示标签名称。
2. 历史数据和本地兜底评估模板仍可能只有名称。
3. 后续做标签重命名、停用、合并时，历史业务含义有可读性。

## 5. 写入流程

后台产品、评估模板、推荐规则写入时：

1. 前端优先提交标签 ID。
2. 后端根据模块范围解析标签 ID。
3. 后端写入 ID 数组。
4. 后端同步写入标签名称快照。

小程序用户评估写入时：

1. 远程评估模板会返回 `tagIds`。
2. 小程序保存本地评估时同时保存 `tags` 和 `tagIds`。
3. 登录后同步评估，后端保存 `tagIds` 和名称快照。
4. 如果只有旧名称，后端会尝试按模块解析成 ID。

## 6. 匹配流程

推荐匹配优先使用 ID：

```text
推荐分数 = 产品优先级 + max(ID 命中数, 名称命中数) * 10 + 推荐规则加分
```

规则命中逻辑：

1. 如果规则有 `conditionTagIds`，使用 ID 全部命中。
2. 如果规则没有 `conditionTagIds`，回退到 `conditionTags` 名称全部命中。
3. 命中后给目标产品增加 `scoreBoost`。

## 7. 标签改名策略

标签字典名称更新时：

1. ID 不变，匹配稳定。
2. 后端同步刷新产品、评估选项、推荐规则、用户评估、线索中的名称快照。
3. 历史记录仍保留 ID，避免改名导致推荐断链。

## 8. 发布步骤

1. 执行 Prisma 迁移，新增 ID 数组字段并按现有名称回填。
2. 重新生成 Prisma Client。
3. 发布 API。
4. 发布 Admin。
5. 小程序可按原流程继续运行；远程模板有 ID 后会自动带上 ID。
6. 后台新增或编辑产品、评估、规则时进入 ID 模式。

## 9. 验收点

1. 标签字典已有标签时，编辑产品选择标签后保存，接口返回 `tagIds` 和 `tags`。
2. 编辑评估模板选项标签后保存，接口返回选项 `tagIds`。
3. 编辑推荐规则命中标签后保存，接口返回 `conditionTagIds`。
4. 小程序提交评估后，用户评估记录保存 `tagIds`。
5. 推荐结果在标签名称不变时与旧逻辑一致。
6. 标签改名后，产品和规则仍能通过 ID 命中。

## 10. 原则说明

KISS：使用数组字段完成第一阶段 ID 化，不额外引入多张关系表和复杂联表查询。

YAGNI：暂不删除旧字段，也不提前做标签图谱、权重和别名。

SOLID：标签解析集中在产品服务内部，写入、展示、匹配职责清晰。

DRY：产品、评估、规则、线索共用统一标签归一化逻辑。
