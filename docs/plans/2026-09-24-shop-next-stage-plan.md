## 目标与当前优先级

先验证商城是否符合真实商品形态和日常运营流程，再决定是否投入真实支付联调。当前工作区已有微信支付 V3 适配器、退款查单和异常核查相关代码，但这些改动尚未提交，也未完成微信商户联调；支付开关必须保持关闭，不能视为可收款能力。

本计划调整为以下顺序：

1. 盘点实际待售商品，确认商品是否存在影响价格、库存或履约的规格，并走查商品维护到订单发货的非支付流程；
2. 若 SKU 是实际销售阻塞，先设计并实现贯通 API、管理端、小程序、购物车、订单快照和库存的最小 SKU 闭环；若不是，则维持单商品单价格；
3. 完成非支付业务验收，记录阻塞项和业务结果；
4. 仅当近期目标明确为真实收款，且商户联调、回调域名和密钥条件具备时，再恢复支付联调与上线门禁工作。

支付安全与生产上线门槛仍然有效，但不再自动构成当前开发的主线。Task 1–4 的支付、退款和迁移实施记录保留为历史执行记录，其中仍标注未完成的事项继续保持未完成，不代表本轮继续扩展支付范围。

## 本轮决策门

SKU 需求目前有明确的用户反馈信号，但规格维度、是否影响价格/库存、商品数量和售后差异尚未确认。确认前不新增 Prisma 模型或迁移，也不做仅有管理端输入框的局部实现。

决策时至少收集：

- 当前及近期计划销售的商品清单，以及每个商品的规格维度和可选值；
- 不同规格是否有独立价格、库存、图片、条码或履约差异；
- 加购、下单、取消、发货和退款时需要保留哪些 SKU 信息；
- 预计首批 SKU 数量及后台日常维护方式。

如果所有待售商品实际都只有一个可售版本，继续采用现有单商品模型；如果规格改变价格、库存或履约，则按 SKU 级库存和价格设计完整闭环。

## 调整后的阶段与验收

### 阶段 A：商品与运营流程核验

- 核对商品分类、上架状态、库存维护和小程序展示是否符合当前商品运营方式。
- 在不发起真实支付的前提下走查浏览、加购、结算信息校验、订单创建/取消和后台订单查询。发货流程仅在隔离测试环境中存在合法的已支付测试订单时验证；否则明确记录该项依赖支付、暂未覆盖，不伪造支付状态或手工改库。
- 将 API/页面缺陷与产品需求分开记录；不通过伪支付或人工改库制造“已支付”状态。
- 验收产物：商品/SKU 需求表、流程检查结果、阻塞项及其优先级。

### 阶段 B：按需实现 SKU

仅在阶段 A 证明 SKU 是真实阻塞时启动。API、管理端、小程序、购物车、库存预留、订单项快照必须作为一个纵向闭环评估；先写模型与状态迁移设计，再实现，不拆成“先加表单、以后补订单”的半成品。

验收至少覆盖：不同 SKU 价格与库存隔离、并发下单不超卖、购物车保留所选 SKU、订单历史快照不受商品后续编辑影响，以及取消/退款库存规则一致。

### 阶段 C：非支付业务验收

- 用真实商品数据验证管理端维护与小程序展示，不访问或修改生产数据。
- 运行相关单测、类型检查和构建；数据库迁移仅在设计确认后进入隔离环境验证。
- 保持支付开关关闭，支付异常代码仅做现状维护，不新增渠道重试、证书轮换或运营功能。

### 阶段 D：真实支付（条件启动）

只有在业务明确要求近期真实收款，并准备好商户联调环境、回调 URL、密钥注入和责任人后启动。复用本计划已记录的支付状态恢复、退款查单、适配器测试和上线清单；未完成商户端到端验证及审批前，不开放真实交易。

## 当前风险与决策

### 延迟支付通知与过期关单

过期任务会把未付款订单取消并释放预留库存；如果支付实际成功但通知延迟到达，当前支付回调无法确认已取消订单，也没有补偿退款或人工核查记录。

必须先确定并实现策略：

- 关单前向微信查询/关闭订单，不能只根据本地过期时间释放库存；
- 对已确认关闭的订单释放预留库存；
- 若本地已关单后仍收到真实成功通知，持久化异常事件并进入补偿退款/人工处理流程，不得重新扣减可能已售出的库存；
- 重复通知和重复补偿必须幂等。

具体微信关单、查单接口行为以支付 V3 接入设计和商户联调为准；没有外部结果确认时，订单应保持可核查状态，而不是猜测成功或失败。

### 退款调用失败或结果未知

管理员批准退款后，记录会先进入 `processing`，再请求支付渠道。外部请求抛错或超时时，记录可能永久停留在处理中。

必须保留稳定的商户退款单号及请求金额，并区分“明确失败”和“结果未知”。明确失败可在核实渠道状态后重试；未知结果先查单/对账，禁止直接生成新退款单重复退款。后台要能查询异常记录及操作历史；人工处理需记录操作者、理由和渠道核对结果。

### 数据迁移与环境基线

当前 Schema 和商城初始迁移需逐字段核对。编码前先检查 migration history、生产/测试目标数据库的 Prisma migration 状态以及迁移 SQL；确认是否存在未迁移的 Schema 变更。任何迁移须生成、审查、在隔离环境验证，并准备备份与回滚/恢复步骤。不得在此计划下重置数据库或直接对共享/生产数据库执行未审查迁移。

## 推迟范围

以下功能不属于本计划，需以真实业务需求和交易稳定性为启动条件另行设计：

- 多规格 SKU 与 SKU 级库存；
- 虚拟兑换码、课程/场地预约和自动履约；
- 第三方商家入驻、商家数据隔离与店铺后台；
- 微信支付自动分账、平台佣金、结算和提现；
- 优惠券、秒杀、拼团、个性化推荐和独立消息队列。

如果 SKU 已成为当前销售阻塞，先收集商品规格数量、库存差异、价格差异、订单快照和售后规则，再单独调整本计划；不能只在管理端增加规格输入框而不扩展订单、库存和退款模型。

## 推进决策

**当前推荐顺序：** 阶段 A 商品与运营流程核验 → 阶段 B（仅在确有 SKU 阻塞时）→ 阶段 C 非支付验收 → 阶段 D（仅在真实收款成为近期目标时）。

不再使用“安全优先就必然先做支付”的默认假设。支付异常恢复和真实联调仍是开放真实交易的硬门槛，但在没有近期收款目标时，将更多支付能力提前开发会增加复杂度而不验证商品需求。

## 原则与风险

- **KISS / YAGNI：** 先以实际商品确认是否需要 SKU；不为了未来假设做通用规格引擎，也不在无收款计划时继续扩展支付。
- **SOLID：** 若实施 SKU，规格与 SKU 级价格/库存由商品域维护；订单、库存、支付渠道继续保持各自职责，不将规则塞进页面或控制器。
- **DRY：** 商品、SKU、订单项快照由 API 定义统一契约，管理端和小程序消费同一模型，避免两端分别推导价格或库存。
- **安全与运维风险：** 支付私钥泄露、回调公网不可达、数据库 migration drift、退款结果未知和通知延迟均为上线阻断项；通过密钥管理、联调演练、迁移审查、告警及人工恢复预案控制。
