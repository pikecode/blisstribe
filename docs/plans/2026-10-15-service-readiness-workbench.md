日期：2026-10-15。范围：后台与 API，沿用现有业务表，无新增数据库迁移。

## 1. 方案与取舍

采用现有套餐列表增加检查入口、工作台增加真实待办的方案；另一种方案是重建产品工作区统一所有配置，适合后续完整的信息架构调整，但本轮会扩大改动范围。

- KISS：运营从当前页面直接看到问题和处理入口。
- DRY：服务端统一计算检查结果，复用现有库存、机构、时段及业务状态。
- SOLID：检查用于配置反馈；下单仍由原资格、库存与交易校验负责最终判定。
- YAGNI：本轮不扩展机构权限、财务账本或自动结算。

## 2. 上架与可售检查

套餐列表显示检查摘要，点击打开检查面板。草稿点击上架也先进入面板。

| 检查项 | 是否阻止上架 |
| --- | --- |
| 关联服务产品有效、机构有效 | 是 |
| 至少一个服务项目、次数合法 | 是 |
| 金额与分摊校验通过 | 是 |
| 预约和退款规则完整 | 是 |
| 关联实物规格有效且退货说明完整 | 是 |
| 产品及分类启用、可被浏览 | 否，提示展示待完善 |
| 机构存在可预约且未满的未来时段 | 否，提示暂不可售 |
| 关联规格可用库存足够 | 否，提示暂不可售 |

同一规格在多个项目出现时，按合计数量检查库存。时段和规格按列表批量读取，避免每个套餐分别查询。

失败项提供产品、机构、套餐编辑、预约时段或商城商品处理入口。检查加载失败允许重试，并禁用上架按钮。需要资格评估单独提示，不把所有套餐判为不可售。

“可售条件就绪”表示当前配置和资源检查通过，不代表每个用户都能立即支付。用户资格、请求时库存和其他交易条件仍以下单实时校验为准。检查不预占库存和预约容量。

## 3. 工作台待办

替换原写死的漏斗示例，移除无真实依据的趋势百分比。六类待办均使用数据库计数：

1. 待确认预约：pending。
2. 今日待接待：confirmed，预约申请时间在北京时间当日。
3. 待审核退款：pending。
4. 退款处理中：processing。
5. 待受理异议：submitted。
6. 逾期异议：未结案且超过处理期限。

点击卡片进入对应列表并带入筛选条件。计数可能重叠，不能直接相加作为唯一工单总数。加载失败显示重试，不将失败展示成零条。
