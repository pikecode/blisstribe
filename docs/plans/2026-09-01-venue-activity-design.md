# 活动场地能力设计

## 1. 目标

引入“场地”作为独立业务实体，让后台可以维护场地资料、图片、可用时间和临时不可用时间，并在创建或发布线下/混合活动时选择场地。

本阶段要解决：

- 场地资料可复用，不在每个活动中重复填写。
- 活动选择场地后能展示场地名称、地址和图片。
- 发布活动时校验场地时间，避免同一场地被重复占用。

本阶段不做：

- 场地对外预约。
- 场地计费和押金。
- 审批流。
- 日历拖拽排期。
- 多门店复杂库存式资源管理。

## 2. 方案选择

### 方案 A：活动表直接增加场地字段

优点：改动最小，上线最快。

缺点：场地图片、地址、容量和时间规则会在活动之间重复，后续无法统一维护，也难以校验空闲时间。

结论：不推荐。

### 方案 B：新增独立 `Venue` 模型

优点：场地资料、图片、开放时间和不可用时间可以集中维护；活动通过 `venueId` 选择场地；后续可以扩展场地日历和使用率统计。

缺点：需要新增后端模块、后台页面、活动表单联动和数据库迁移。

结论：推荐。

### 方案 C：完整场地预约系统

优点：长期能力完整。

缺点：当前阶段过重，会把活动运营闭环拖成资源预约系统。

结论：暂缓。

## 3. 数据模型

新增：

```text
Venue 场地基础资料
VenueImage 场地图片
VenueAvailability 每周可用时间
VenueBlockedSlot 临时不可用时间
```

修改：

```text
Activity.venueId
Activity.venueSnapshot
```

`venueSnapshot` 用于保留活动发布或保存时的场地快照，避免场地资料修改后影响历史活动展示。

## 4. 业务规则

线下活动和混合活动可以选择场地，线上活动不强制选择场地。

活动保存或发布时，如果选择了场地，需要校验：

1. 场地存在、启用、未删除。
2. 活动开始和结束时间落在同一天。
3. 活动时间完全落在场地当天可用时间内。
4. 活动时间不与场地不可用时间重叠。
5. 活动时间不与同场地其他已发布活动重叠。
6. 活动名额不能超过场地容量。

第一版采用严格阻止冲突。原因是线下履约风险高，保存草稿时也应尽早暴露排期问题。

## 5. 后台设计

新增后台菜单：

```text
场地管理
```

页面能力：

- 场地列表：名称、城市区域、容量、状态、排序、封面。
- 场地编辑：基础信息、封面、多图、设施、描述、联系人。
- 可用时间：按星期维护 `HH:mm-HH:mm`。
- 不可用时间：维护开始时间、结束时间、原因。
- 状态管理：启用/停用。

活动管理表单增加：

- 场地选择。
- 选中场地后展示地址、容量和可用时间摘要。
- 未填写 `locationText` 时默认使用场地地址。

## 6. 小程序展示

活动列表保持轻量，只展示场地名称或 `locationText`。

活动详情展示：

- 场地名称。
- 地址。
- 封面图或活动封面。
- 设施标签。

第一版不接微信地图导航，后续可基于经纬度扩展。

## 7. 工程原则

- KISS：只做场地维护、活动选择和基础时间校验，不做完整预约系统。
- YAGNI：暂缓计费、审批、日历拖拽、外部预约入口。
- SOLID：`VenueModule` 负责场地资料和时间规则，`ActivityModule` 只负责活动选择与冲突校验调用。
- DRY：场地图片、地址、容量、设施集中维护，活动通过 `venueId` 复用，并通过 `venueSnapshot` 保留历史展示口径。
