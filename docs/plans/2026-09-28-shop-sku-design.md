# 商城 SKU 设计

**日期：** 2026-09-28  
**状态：** 已确认并进入实现  
**范围：** 平台自营实物商品的规格、SKU 价格/库存和交易快照

## 决策

采用“独立 SKU 记录 + JSON 规格组合”：

- 每个商品至少包含一个 SKU；不区分有规格与无规格商品，无规格商品使用空规格默认 SKU。
- 每个 SKU 有独立编码、属性组合、价格、总库存、预留库存、已售库存和启用状态。
- 商品保留名称、描述、分类、图片、上架状态等公共信息。
- 购物车按 SKU 唯一；订单项保存商品名、SKU 编码、规格 JSON、图片、单价和小计快照。
- 服务端从 SKU 读取价格和库存；客户端提交 `skuId` 与数量。
- 为兼容尚未升级的旧客户端，旧 `productId` 只允许解析到恰好一个 SKU 的商品；多 SKU 商品拒绝旧请求，要求选择规格。

## 数据流

```text
商品管理（规格/价格/库存）
  -> 商品详情返回 SKU 列表
  -> 用户选择 SKU
  -> 购物车按 skuId 合并
  -> 下单事务锁定并预留 SKU 库存
  -> 订单项保存 SKU 快照
  -> 支付/取消/退款只变更对应 SKU 库存
```

## 数据迁移

新增 `ShopProductSku`，先按每个现存商品的旧价格与库存回填一个空规格默认 SKU，再为购物车和历史订单回填 `skuId` 与快照，最后在同一迁移中移除商品级价格与库存列，并把购物车唯一约束改为 `(cartId, skuId)`。迁移不执行数据库重置；应用前需先在隔离 schema 重放和检查。

## 边界与取舍

- 当前不做规格字典、无限层级规格组合、SKU 图片库、条码扫描或批量导入。
- JSON 用于保存有限规格值快照，不用作库存/价格查询条件。
- 管理端编辑整个 SKU 列表时，若待删除 SKU 已被购物车或订单引用，服务端拒绝删除；已售 SKU 可停用但保留历史引用。
- 订单和 SKU 的关联只用于追溯；退款/库存处理依据订单项快照数量和关联 SKU，历史展示不依赖 SKU 当前名称或价格。

## 验收

- 单 SKU 商品行为与原流程一致；多 SKU 商品可按规格区分价格和库存。
- 并发下单不会超卖；取消仅释放对应 SKU 的预留库存；支付仅把对应 SKU 的预留库存转为已售；退款回滚对应 SKU 的已售量。
- 购物车不合并不同 SKU；订单历史在 SKU 编辑后保持原规格与价格。
- 管理端能够创建、编辑和停用 SKU；小程序能够选择规格并显示所选 SKU 的价格和余量。
- 隔离迁移、API/Admin/小程序类型检查和构建通过；支付保持关闭且不进行商户请求。

## 工程原则

- **KISS/YAGNI：** 用一张 SKU 表和 JSON 属性快照满足当前多规格需求，不建设通用商品配置平台。
- **SOLID：** 商品服务负责 SKU 校验，库存变更由订单/支付/退款领域流程负责，页面不计算权威价格。
- **DRY：** 商品详情、购物车和订单共用 `skuId`、属性和价格语义。
