# 服务方案后续交付实施计划

**目标：** 按已确认的 V1.2 需求补齐完整产品，逐项记录实现状态。

**架构：** 继续复用服务订单、项目快照、权益、预约与微信支付渠道。套餐服务项目沿用现有明细模型；实物交付、售后、收益与结算各自承担独立职责，避免把库存和财务逻辑混入预约模块。

**技术栈：** NestJS、Prisma、PostgreSQL、Vue 3、Element Plus、UniApp。

## 实施顺序

1. 多项目套餐：修改 `apps/admin/src/views/service-program/index.vue`，维护全部项目、次数、分摊价和每次结算价；修改 `apps/api/src/service-program/offering/offering.service.ts`，校验按次数计算的结算合计。复用现有患者项目选择、权益发放和部分退款接口，不新增订单模型。
2. 套餐实物：关联商城规格，成交保存商品快照，支持库存占用、现场领取或寄送、地址与物流、退货核验；交付和退款状态接入计划状态计算。
3. 服务异议与随访：患者提交异议，运营受理、回复、复核和必要退费；机构登记随访安排与患者反馈。
4. 主理人协助：患者主动确认来源与联系授权；主理人只查看授权业务摘要，预约建议由患者确认。
5. 收益与结算：固化购买时的比例、按实际履约进入观察期，退款冲回，机构与主理人结算单及线下付款登记。
6. 多机构账号：机构范围约束在服务端查询和写入中统一落实，平台角色按客服、财务、管理员限制操作。
7. 交付收尾：构建、部署、运营手册与交付状态更新；真实微信支付、退款到账与真机体验由获授权患者完成外部验收。

## 设计取舍

推荐扩展现有项目明细，复用同一订单和退款规则，符合 KISS、DRY。另建套餐订单可独立演进，但会重复支付和售后逻辑，当前不采用。

项目成交分摊金额是该项目全部次数的总金额，机构结算字段是每次单价。付费套餐按整个方案校验：`全部项目每次结算单价 × 各自次数的合计 + 主理人收益 ≤ 套餐售价`，允许零元赠送项目由其他项目覆盖成本。免费体验的机构结算由活动预算承担，其预算上限和停止发放机制在收益结算阶段补齐。历史订单保持购买时快照，不随方案修改。
