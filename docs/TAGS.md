# 标签使用规范

## 1. 目标

标签是产品推荐的统一语言，用来连接后台维护的产品、用户个人资料、用户提交的评估答案、推荐规则和后续线索跟进。

当前阶段已经采用标签 ID 优先方案：标签由后台统一维护，产品、用户资料、评估选项和推荐规则优先保存标签 ID，同时保留标签名称作为展示快照。这样既能避免标签改名导致推荐断链，也能兼容小程序和历史数据。

## 2. 标签怎么管理

后台入口：`产品运营 / 标签字典`。

每个标签包含以下核心字段：

| 字段 | 用途 |
| --- | --- |
| 编码 | 系统识别用，建议使用英文或拼音，如 `sleep_improve` |
| 名称 | 业务人员看到和选择的标签，如 `睡眠改善` |
| 分组 | 帮助管理和选择，如 `需求方向`、`紧急程度`、`服务方式` |
| 所属模块 | 可绑定健康、美学、亲子等模块；不绑定模块表示通用标签 |
| 状态 | 启用后才能在产品、评估和规则中选择 |
| 排序 | 控制后台选择列表展示顺序 |

维护原则：

1. 优先复用已有标签，不要随手创建同义词。
2. 同一业务含义只保留一个主标签，例如统一使用 `睡眠改善`，不要同时维护 `改善睡眠`、`睡眠问题`。
3. 通用标签用于跨模块场景，例如 `愿意联系`、`线上咨询`、`先了解`。
4. 模块标签用于模块内推荐，例如健康模块的 `睡眠改善`、`体态管理`。
5. 已经被产品或评估使用的标签不要直接改名；如需调整，推荐停用旧标签并新建新标签，再迁移产品和评估配置。

## 3. 产品怎么使用标签

后台入口：`产品运营 / 产品管理 / 编辑产品 / 推荐标签`。

产品标签表示这个产品适合解决什么需求、适合什么咨询方式或人群特征。

选择规则：

1. 选择产品所属模块后，标签下拉会展示通用标签和该模块标签。
2. 下拉按 `模块 / 分组` 分组，例如 `健康 / 需求方向`、`通用 / 服务方式`。
3. `推荐标签` 表示产品整体适配范围，建议控制在 3 到 8 个。
4. `强相关标签` 表示产品最核心的推荐场景，命中后加分最高。
5. `弱相关标签` 表示产品可以覆盖但不是主场景的需求。
6. `排除标签` 表示用户命中这些标签时不推荐该产品。
7. 产品标签应描述产品能力，不要描述营销话术。例如使用 `睡眠改善`，不要使用 `爆款推荐`。

示例：

| 产品 | 推荐标签 |
| --- | --- |
| 深度睡眠调理套餐 | `睡眠改善`、`重点改善`、`线上咨询` |
| 体态评估与训练方案 | `体态管理`、`先了解`、`到店体验` |

## 4. 评估怎么使用标签

后台入口：`产品运营 / 评估模板管理`。

评估模板归属于一个产品模块。每道题目前支持单选，每个选项可以绑定多个标签。用户提交评估后，系统会把选中选项上的标签合并为用户本次需求标签。

维护规则：

1. 每个模块可以维护启用中的评估模板，小程序优先读取后台配置。
2. 题目标识 `key` 用于系统记录，建议使用英文或拼音，如 `focus`、`service_mode`。
3. 题目标题面向用户展示，应简短直接。
4. 选项值 `value` 建议稳定，不要频繁变更。
5. 选项标签应表达用户意图，例如 `尽快改善`、`愿意联系`、`睡眠改善`。
6. 每个选项标签可以配置权重，范围 1 到 5；不配置时默认为 1。
7. 权重只表达该选项对用户需求强度的影响，不用于医学或专业诊断。

示例：

| 题目 | 选项 | 选项标签 |
| --- | --- | --- |
| 你现在最关注什么？ | 睡眠和精力 | `睡眠改善` |
| 你希望怎么开始？ | 先线上聊一聊 | `线上咨询`、`愿意联系` |
| 你希望改善节奏？ | 越快越好 | `尽快改善`、`重点改善` |

## 5. 个人资料怎么使用标签

小程序入口：`我的 / 资料与标签`。

个人资料里的自我标签表示用户的长期偏好和基础画像，例如 `健康养生`、`运动健身`、`亲子育儿`、`职场进阶`。

当前实现：

1. 小程序从公共接口 `GET /tags` 读取后台启用标签。
2. 标签按 `模块 / 分组` 展示，例如 `通用 / 生活方式`、`健康 / 健康`。
3. 用户最多选择 5 个自我标签。
4. 保存资料时同时提交 `tagIds` 和 `tags`。
5. 服务端以 `tagIds` 和 `tags` 到标签字典中校验，只保存启用标签。
6. `User.tagIds` 是推荐匹配主键，`User.tags` 是展示快照和历史兼容。

个人资料标签和评估标签的定位不同：

| 来源 | 含义 | 推荐作用 |
| --- | --- | --- |
| 个人资料标签 | 长期偏好、稳定兴趣 | 作为推荐底色，帮助冷启动 |
| 评估标签 | 当前需求、即时意图 | 作为主要推荐依据 |
| 咨询标签 | 用户提交咨询时的需求快照 | 用于后续跟进和运营分析 |

维护建议：

1. 个人资料可选标签不宜过细，优先使用稳定兴趣类标签。
2. 评估选项标签可以更细，例如 `睡眠改善`、`尽快改善`、`线上咨询`。
3. 用户自我标签不要承担专业诊断含义，只用于偏好表达。
4. 后台停用标签后，小程序不会再展示给用户选择；历史用户仍保留名称快照，但后续保存会重新按启用标签规范化。

## 6. 推荐规则怎么使用标签

后台入口：`产品运营 / 推荐规则管理`。

推荐规则用于增强基础标签匹配。当用户本次评估标签包含规则配置的全部命中标签时，指定产品获得额外加分，并优先展示规则推荐理由。

维护规则：

1. 推荐规则必须绑定模块和产品。
2. 命中标签建议控制在 1 到 3 个，过多会导致规则很难命中。
3. 加分用于控制推荐强度，常规规则可设置 20 到 50，强推荐规则可设置 60 到 100。
4. 推荐理由是用户可见文案，应解释为什么推荐该产品。

示例：

| 规则 | 命中标签 | 推荐产品 | 加分 |
| --- | --- | --- | --- |
| 睡眠重点改善推荐 | `睡眠改善`、`重点改善` | 深度睡眠调理套餐 | 80 |
| 线上咨询优先推荐 | `线上咨询`、`愿意联系` | 专家线上咨询 | 50 |

## 7. 标签怎么匹配

当前推荐分数由三部分组成：

```text
推荐分数 =
产品优先级
+ 强相关标签命中权重分
+ 弱相关标签命中权重分
+ 普通标签命中兜底分
+ 推荐规则加分
```

匹配过程：

1. 用户维护个人资料标签，系统保存 `User.tagIds` 与 `User.tags`。
2. 用户提交某个模块的评估，系统收集评估选项上的标签 ID 和名称，形成评估 `tagIds` 与 `tags`。
3. 系统查找同模块下已上架产品。
4. 如果用户标签命中产品 `excludeTagIds`，该产品不进入自动推荐结果。
5. 产品强相关、弱相关、普通标签分别按不同分值计算基础分。
6. 推荐规则的 `conditionTagIds` 全部包含在用户 `tagIds` 中时，目标产品获得额外加分；旧规则会回退到名称匹配。
7. 系统按推荐分数、产品优先级、排序展示推荐产品。

默认分值：

| 类型 | 分值 |
| --- | --- |
| 强相关标签 | 标签权重 * 20 |
| 弱相关标签 | 标签权重 * 10 |
| 普通标签 | 标签权重 * 5 |
| 旧名称命中 | 10 |

当前阶段的主匹配键是标签 ID，标签名称用于展示和历史兼容。标签改名时，系统会同步刷新产品、评估选项、推荐规则、用户评估和线索里的名称快照。

## 8. 标准维护流程

新增一个产品并进入推荐链路时，按以下顺序操作：

1. 在标签字典中确认需要的标签是否存在。
2. 如果标签不存在，先创建标签并设置分组、模块、状态。
3. 在产品管理中新增或编辑产品，选择推荐标签、强相关标签、弱相关标签和排除标签。
4. 在评估模板中确认相关选项是否绑定了同一批标签，并按需要调整权重。
5. 如需强推荐，在推荐规则中配置命中标签、目标产品和推荐理由。
6. 到小程序提交一次评估，确认推荐结果、推荐理由和线索记录是否符合预期。
7. 到小程序资料页选择相关自我标签，确认冷启动推荐结果是否符合预期。

## 9. 当前边界与后续扩展

当前方案遵循 KISS 和 YAGNI：先完成标签 ID 化和推荐链路稳定性，不提前引入复杂画像系统。

后续可扩展方向：

1. 标签别名：支持 `睡不好`、`失眠` 合并到 `睡眠改善`。
2. 规则条件升级：支持任一命中、全部命中、排除标签、组合条件。
3. 模板版本发布：评估模板编辑后先保存草稿，确认后再发布新版本。
4. 用户画像沉淀：把多次评估和咨询结果合并为长期用户标签。
5. 标签使用场景：为标签增加 `profile`、`assessment`、`product` 等场景字段，进一步控制小程序可选范围。
6. 用户标签权重：区分自选标签、评估标签、咨询标签和行为标签的权重。

## 10. 工程原则说明

KISS：当前采用数组字段完成第一阶段 ID 化，避免一次性引入多张关系表和复杂联表查询。

YAGNI：暂不实现复杂画像表、标签来源衰减和规则表达式，等真实运营数据验证后再升级。

SOLID：标签分组选项抽为管理端工具函数，页面只负责业务表单。

DRY：产品、评估、推荐规则共用同一套标签分组展示逻辑，减少重复实现。
