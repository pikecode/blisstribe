# BlissTribe 当前进度与后续规划

> 更新时间：2026-08-31

## 1. 文档目的

本文档汇总 BlissTribe 当前研发进度、已具备的业务闭环、主要风险和下一阶段规划，作为后续排期、验收和上线准备的统一参考。

## 2. 当前整体判断

当前项目已经从“注册登录 MVP”推进到“推荐、线索、活动、B 端伙伴”并行可验收阶段，核心链路如下：

```text
后台维护模块、标签、评估、产品、推荐规则、活动
  ↓
小程序用户登录、完善资料、完成评估
  ↓
系统基于标签、规则和权重推荐产品或活动
  ↓
用户提交咨询线索或活动报名
  ↓
后台查看线索、报名、推荐效果并进行跟进
```

整体技术路线仍保持 monorepo 模块化单体，适合当前团队规模和业务验证阶段。下一阶段重点不应继续横向堆功能，而应把“可运营、可观测、可发布、可复盘”补齐。

## 3. 已完成进度

### 3.1 工程基础

- 已建立 `pnpm workspace` monorepo，包含 `apps/miniapp`、`apps/admin`、`apps/api`、`packages/shared`。
- 已具备 NestJS API、Vue 3 后台、uni-app 微信小程序、Prisma、PostgreSQL、Redis 的基础工程结构。
- 已配置本地 Docker Compose、ACR 镜像发布脚本和生产 Docker Compose 部署文档。
- 已沉淀 `README.md`、架构、API、数据库、前端、安全、上线清单等基础文档。

原则应用：

- KISS：继续采用模块化单体，避免过早拆微服务。
- SOLID：三端和共享包职责清晰，后续扩展可按业务模块推进。

### 3.2 用户与认证

- 已支持微信登录、新用户临时态、手机号授权、注册、Token 登录态和刷新。
- 已支持用户资料、头像上传、协议版本和用户协议确认记录。
- 已支持后台管理员登录和管理入口。

当前缺口：

- 生产环境默认管理员密码、JWT 密钥、微信配置必须在上线前替换。
- 需要补充更完整的异常链路验收，如 token 过期、微信接口失败、上传失败。

### 3.3 S2B2C 伙伴基础

- 已建立 `Partner`、`PartnerMember`、`CustomerRelation`、`RelationEvent`、`InvitationCode`、`InvitationRecord` 等模型基础。
- 已具备 B 端入驻申请、后台审核、邀请入口、客户归属和小程序 B 工作台页面。
- 后台已有服务伙伴审核页面，小程序已有入驻、邀请客户、客户列表等页面。

当前缺口：

- B 端客户经营仍偏基础，缺少跟进记录、转化状态、业绩统计和收益视图。
- 佣金、结算、订单和提现还未进入实现范围，符合当前 YAGNI 策略。

### 3.4 产品与精准推荐

- 已支持产品模块、标签字典、评估模板、评估选项、推荐规则、产品管理。
- 产品已升级为统一供给模型，支持 `service`、`physical`、`package` 三类 `productType`。
- 推荐链路已支持标签 ID 化、标签名称快照、强相关标签、弱相关标签、排除标签、评估权重和规则加分。
- 已支持推荐事件上报、推荐效果后台分析、咨询线索创建、后台线索跟进摘要。
- 小程序已有产品列表、评估、详情、我的咨询和咨询详情页面。

当前缺口：

- 推荐效果需要从“有事件记录”升级到“能指导运营决策”，例如按模块、产品类型、推荐形式、线索状态分析。
- 推荐事件、线索、评估之间的归因链路还需要进一步标准化。

### 3.5 活动发布与报名

- 已新增独立 `ActivityModule`，没有把活动混入产品模型。
- 已建立 `Activity`、`ActivityRegistration` 数据模型和迁移。
- API 已支持公开活动列表、推荐活动、活动详情、用户报名、取消报名、我的报名。
- 后台已支持活动列表、活动创建/编辑、发布/下线、报名列表、报名详情和状态更新。
- 小程序已接入活动列表、活动详情、报名和我的活动页面。
- 本地冒烟脚本已覆盖活动列表、推荐活动、后台活动列表和后台报名列表。

当前缺口：

- 第一版活动暂不包含支付、签到、候补、通知、分销结算，符合 YAGNI。
- 活动曝光、点击、报名转化的数据归因还需要接入统一分析口径。

### 3.6 本地验收与发布基础

- `scripts/check-local.sh` 已覆盖后台登录、标签、产品、推荐列表、推荐事件、推荐分析、线索摘要、活动列表、推荐活动、后台活动和后台报名。
- 已有 `docs/GO_LIVE_CHECKLIST.md` 描述生产发布、安全组、HTTPS、密钥、数据库迁移和小程序验收。
- 已有 `scripts/deploy-acr.sh` 和 Dockerfile 支撑镜像发布。

当前缺口：

- 自动化测试仍以冒烟脚本为主，缺少单元测试、接口测试和前端端到端测试。
- 生产监控、日志聚合、备份恢复演练和灰度回滚验证还未形成制度化流程。

## 4. 当前主要风险

| 风险 | 影响 | 建议 |
| --- | --- | --- |
| 测试覆盖不足 | 修改推荐、报名、线索等链路时容易引入回归 | 先补 P0 接口测试和本地冒烟脚本，再逐步加端到端测试 |
| 运营分析口径分散 | 有数据但难以判断推荐和活动是否有效 | 统一事件模型、推荐形式、来源场景、转化状态 |
| 生产安全配置待完善 | 默认账号、密钥、HTTP、数据库暴露会带来上线风险 | 上线前逐项执行 `docs/GO_LIVE_CHECKLIST.md` |
| B 端经营闭环偏弱 | B 能邀请和查看客户，但难以持续经营 | 增加客户跟进、线索分配、活动推广和转化统计 |
| 管理后台生成产物混入源码目录 | `apps/admin/src` 下存在 `.js`、`.map` 文件，可能干扰审查和维护 | 确认生成来源，统一清理或调整构建输出路径 |

## 5. 后续推进方案

### 方案 A：先补运营闭环

目标：让平台能清楚看到推荐、线索、活动和 B 端转化效果。

适用场景：

- 准备进入真实用户测试。
- 需要判断哪些产品、活动和推荐策略有效。
- 需要运营人员持续维护内容和跟进用户。

优点：

- 能尽快形成数据复盘能力。
- 有利于后续订单、佣金和智能推荐。
- 直接服务业务增长。

缺点：

- 需要同时改 API、后台和小程序。
- 验收标准不只看页面，还要看数据链路是否闭环。

### 方案 B：先补发布稳定性

目标：把当前功能稳定部署到公网测试或生产环境。

适用场景：

- 近期需要提交小程序体验版或正式版。
- 需要对外演示或邀请种子用户试用。
- 团队希望先降低环境和发布风险。

优点：

- 能尽快进入真实环境验证。
- 有助于暴露微信、HTTPS、域名、上传、权限等环境问题。
- 对后续迭代交付节奏有帮助。

缺点：

- 对运营效果提升不直接。
- 如果业务闭环口径还不稳定，过早发布会增加返工。

推荐顺序：

```text
方案 A 运营闭环
  ↓
方案 B 发布稳定性
  ↓
体验优化和增长功能持续迭代
```

理由：当前功能已经覆盖产品、线索、活动和 B 端基础，不宜继续只做页面。优先补数据和运营闭环，可以让后续每个功能都能被验证；发布稳定性紧随其后，确保真实环境可持续交付。

## 7. 近期 P0 任务清单

### 7.1 运营分析口径统一

- 定义统一事件字段：`sourceScene`、`recommendationForm`、`moduleCode`、`productType`、`activityId`、`partnerId`、`inviteCode`。
- 将产品推荐、产品详情、咨询线索、活动列表、活动详情、活动报名纳入统一转化漏斗。
- 后台补充按推荐形式、产品类型、活动、B 来源维度的统计查询。

验收标准：

- 能回答“用户从哪个入口看到什么内容、是否点击、是否提交线索或报名”。
- 能按产品和活动维度看到曝光、点击、转化数据。

### 7.2 P0 自动化验收

- 扩展 `scripts/check-local.sh`，覆盖活动报名的登录态链路和线索详情链路。
- 为 API 核心服务补充最小接口测试或服务测试：认证、产品推荐、线索、活动报名、后台审核。
- 增加迁移后 Prisma Client 生成和类型检查到本地验收流程。

验收标准：

- 本地一条命令能检查主链路。
- 推荐、线索、报名任一核心改动后能快速发现回归。

### 7.3 发布稳定性

- 按 `docs/GO_LIVE_CHECKLIST.md` 完成生产密钥、默认密码、HTTPS、小程序合法域名配置。
- 明确数据库迁移执行顺序和失败回滚办法。
- 建立 PostgreSQL 备份与恢复演练记录。
- 补充 `/health` 或等价健康检查接口，并纳入部署验收。

验收标准：

- 生产部署后可通过公网域名访问后台和 API。
- 小程序体验版能完成登录、评估、推荐、线索、活动报名主链路。
- 发生失败时能回滚到上一个镜像版本。

## 8. 暂缓事项

以下能力先记录但不进入近期 P0：

- Kubernetes、服务网格、微服务拆分。
- 完整商城、SKU、库存、物流、售后。
- 自动打款、提现、复杂佣金结算。
- 多级分销和复杂渠道风控。
- AI 自动训练推荐模型。
- 复杂 CRM 自动化营销。

暂缓原因：这些能力依赖真实转化数据和稳定运营流程。当前先补数据闭环和发布稳定性，更符合 YAGNI 和 KISS。

## 9. 工程原则复盘

- KISS：保持 monorepo + 模块化单体，优先补主链路和可观测能力，不引入复杂基础设施。
- YAGNI：订单、佣金、支付、智能推荐先不实现，等产品、活动和线索转化验证后再启动。
- SOLID：用户、伙伴、产品、活动、推荐、线索、统计继续按模块边界演进，避免一个模块承载过多职责。
- DRY：标签、产品模块、推荐规则、活动归属、来源场景等业务口径应由后台和 API 统一维护，小程序只消费接口数据。

## 10. 下一步建议

建议先启动“阶段 1：运营分析口径统一”。这是当前从可演示系统走向可运营系统的关键步骤，也能为活动、产品、B 端和后续订单结算提供共同的数据底座。

建议拆成三个小迭代：

1. 统一事件字段和转化漏斗定义。
2. API 写入和查询口径补齐。
3. 后台看板展示和本地验收脚本扩展。

完成后再进入生产发布加固，避免把尚不可复盘的业务链路过早推到真实环境。
