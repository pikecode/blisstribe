# 产品设计评估与优化建议

日期：2026-10-15。依据：当前后台、小程序与服务业务代码、交付状态文档，以及本轮真实操作反馈。本文是产品与交互评估，不代表所有业务分支已验收，不作为医疗判断依据。

## 1. 评估结论

现有系统已经具备介绍、咨询、购买、预约、核销、售后的业务基础。主要问题是不同阶段的入口和状态没有充分衔接：用户不知道下一步做什么，运营需要跨页面查找同一产品的配置。

建议沿用现有业务模块，优先串联患者下一步操作与运营待办，再完善配置发布和机构协作。不要先扩展更多产品类型。

## 2. 统一业务概念

| 概念 | 职责 | 不应承担的职责 |
| --- | --- | --- |
| 服务产品 | 用户理解服务的介绍页，承载封面、适用对象、内容和服务方式 | 不用价格文案决定实际扣款 |
| 服务套餐 | 用户购买的具体配置：售价、项目、次数、期限、机构、规则 | 不以“套餐”名称推断是否包含实物 |
| 套餐项目 | 服务或实物；分别核销次数或交付数量 | 实物不进入预约流程 |
| 商城商品 | 实物规格、库存和独立售卖；也可被套餐引用 | 不复制一套套餐库存 |
| 咨询记录 | 需求沟通与跟进 | 沟通确认不等于机构购买资格 |
| 购买资格 | 指定用户在指定套餐下的购买条件 | 不替代订单支付状态 |
| 服务订单 | 成交与支付、退款记录 | 不用单一订单状态概括全部履约 |
| 我的服务 | 用户持有的次数、预约、实物、随访和售后事项 | 不要求用户理解内部权益字段 |

例：一个服务产品关联体验套餐和多次套餐；多次套餐可以包含服务 6 次与用品 1 件。实物来自商城商品，服务与实物按各自流程履约。

## 3. 本轮已实施的入口调整

- 后台新增入口改为“新增服务产品”，类型固定为服务产品。
- 历史实物和组合记录继续显示、筛选、编辑内容，名称标识为历史介绍；编辑时保留原类型，避免误改类型影响关联业务。
- 页面说明介绍与套餐的职责，并提供商城商品入口。
- 列表“价格”改为“价格文案”，表单解释实际成交价在套餐维护。
- 产品、套餐、订单等原有地址继续使用，不批量转换历史数据。

此处属于后台创建入口收敛，现有 API 仍兼容旧类型；如将来开放外部运营客户端，再单独制定接口创建策略与历史迁移规则。

## 4. 优先改进项

### P0：购买主入口与购买条件

**现状证据**：`apps/miniapp/src/pages/products/detail.vue` 已显示套餐卡片，但底部固定按钮仍调用提交需求；提交过咨询时显示禁用的“已提交需求”。`pages/profile/product-lead-detail.vue` 确认沟通后仍主要展示“查看产品”。这已经引发用户误认为不能购买的反馈。

**建议方案**：

- 有可售套餐的产品，底部主按钮显示“选择套餐”，咨询为次操作；已提交咨询不能禁用套餐入口。
- 仅能咨询的产品保留咨询主按钮，展示已有咨询进展。
- 套餐页先显示当前购买条件和阻塞原因，再给出对应操作：可购买、等待机构确认、暂无时段、实物缺货、已下架。
- 咨询详情展示已确认可购的套餐，并给出直接进入套餐的入口；未确认资格时清楚展示等待事项。
- 套餐加载失败展示重试；不把接口失败当成“没有套餐”。当前详情将套餐请求错误转为空数组，需要调整。

**验收**：用户完成沟通后，从咨询详情至套餐确认页最多两次点击；不重复提交咨询；服务端继续执行购买资格与库存校验。

### P0：区分需求问卷、沟通进展、购买资格

**现状证据**：首页 `ModuleAssessmentList.vue` 使用完成与否统一显示“待评估”，没有依据模块是否开启问卷区分；后台资格与咨询状态是不同记录。

**建议方案**：首页模块改为“服务分类”，未开启问卷的模块显示“查看服务”；开启问卷的模块提供“了解需求”与“浏览服务”。机构确认资格只出现在对应套餐及咨询记录中。问卷完成后不能自动获得购买资格。

**验收**：无需问卷的产品不会显示待评估；完成沟通不会误显示购买资格已获批。

### P0：清晰表达可售状态与上架前缺项

**现状证据**：套餐发布校验关联、金额与规则；购买时还校验机构开放时段、套餐实物库存和用户资格。因此“已上架”不保证当前用户可买。

**建议方案**：运营侧分别显示“展示状态”和“可售准备情况”。上架前展示产品状态、机构状态、价格分摊、规则、时段和实物规格检查清单；无时段、缺货需给出修复入口。用户资格属于用户维度，不应把个别用户无资格误标为套餐全局不可售。

**验收**：运营可以从套餐列表知道当前为何不能成交；已有页面跳转到相应配置，不重复维护同一字段。

### P0：操作结果必须反映实际保存结果

**现状证据**：后台 `apps/admin/src/views/product/index.vue` 的 `deleteModule` 函数中，删除接口调用被注释，仍然提示“模块已删除”。这是明确的反馈错误，不能作为删除完成的依据。

**建议方案**：在接口与关联数据删除策略明确前禁用删除并说明原因；如需清理模块，优先提供停用入口。实际删除必须成功返回后才显示成功，存在产品引用时提示关联项并阻止删除。

**验收**：取消、失败、存在引用和成功四种结果提示准确，刷新后状态与提示一致。

### P1：服务产品作为配置起点

**现状**：已经增加“管理套餐”快捷入口，但介绍、机构、套餐、时段仍分散维护。

**建议方案**：产品工作区显示“介绍、套餐、上线检查”三个页签；套餐关联机构与时段入口，按缺项引导。服务产品列表显示上架套餐数、可售最低价与准备状态。先保留现有页面，逐步复用到工作区。

**价格规则**：可售套餐价格由系统汇总展示；没有可售套餐时使用“咨询后确认”。若保留营销价格文案，应单独标注，不能覆盖支付金额。

**验收**：从创建介绍到发布首个套餐有明确下一步；运营不会误以为保存介绍已完成售卖配置。

### P1：表单复杂度与安全编辑

**现状**：套餐编辑已支持摘要、分摊提示、只读与下架编辑；每个项目仍要求运营手工填写分摊和结算。

**建议方案**：

- 单服务项目在用户确认后将套餐价填入该项目分摊；多项目提供“按次数分摊”与“手动分摊”，自动结果允许调整。
- 自动分摊以分为单位，明确尾差分配，确认前展示结果；不能在输入过程中静默重算已填写金额。
- 项目较多时可收起已完成的项目卡片，错误项目自动展开定位。
- “保存草稿”允许逐步补全；“上架”执行完整必填校验。当前表单仍要求预约和退款规则后才能保存。
- 下架编辑会暂停新购买，当前流程保留。后续高频更新时再考虑“编辑新版本、确认后替换”，避免提前引入版本审批复杂度。

**验收**：分摊总额等于售价，旧订单快照不被改写；未保存退出有提示；财务含义不因自动填写而改变。

### P1：按待办组织运营操作

**现状**：后台已按服务经营归类，预约有今日接待，但退款、异议、随访等散布在不同列表或订单详情。

**建议方案**：在工作台增加“待确认预约、今日接待、待审核退款、待处理异议、今日随访”等待办数量，点击进入已筛选列表；标出责任人、剩余时限及逾期。订单详情保留完整时间线。

**验收**：运营进入后台就知道今天处理什么；完成事项退出待办，失败/未知资金结果继续留在处理中。

### P1：患者服务中心和消息入口

**现状**：已有我的服务与消息页面。本轮应用户测试要求，`pages/services/notices` 已设为普通编译及正式构建默认页；消息页空态只有“暂无服务消息”，不适合新用户探索服务。

**建议方案**：商业上线时优先采用“首页、我的服务、我的”导航，消息作为服务中心入口，未读数可见。如果决定保留消息首页，则需补充未登录引导、空态“浏览服务”、我的服务入口及返回主导航的方式。

**本轮处理**：保留用户已指定的默认页，仅列出上线设计选择，不擅自改回首页。

**验收**：未登录、新注册、没有消息三种情况下，都能找到浏览服务入口；登录后能继续原操作。

### P1：收益配置与交付能力一致

**现状依据**：套餐已维护默认推广收益比例和机构结算单价，交付状态文档明确收益账本、结算及多机构账号隔离未交付。

**建议方案**：在运营配置处说明这些字段当前用于规则配置及预算校验，不表示已自动打款。独立结算能力完成前，不提供“已结算”或“可提现”等无实际依据的状态。

**验收**：运营能区分配置金额、应计金额和实际结算；退款或异议关联收益处理时，有实际账本和对账证据。

### P2：多机构协作与细分权限

**现状**：机构可以维护数据，当前后台主要使用平台管理权限，多机构独立账号与数据范围尚待交付。

**建议方案**：先定义平台运营、机构接待、财务审核的职责与数据范围，再支持机构自助登录。医生护士可继续线下履约，由授权接待人员记录实际执行人；保留审计，避免为了上平台增加角色负担。

**验收**：机构之间数据隔离；财务与履约异议独立处理规则可以由实际账号完成，而不是共享账号代替。

## 5. 实施顺序与方案比较

| 方案 | 适用情况 | 成本与取舍 |
| --- | --- | --- |
| 推荐：沿现有模块串联入口与状态 | 当前单机构试运营 | 改动集中、可逐步验收，先解决可发现和可操作问题 |
| 重建统一商品与流程平台 | 多机构、多交易模型已明确且资源充足 | 迁移与兼容成本高；当前还会放大用户概念负担 |

建议顺序：本次创建入口收敛 → 操作结果准确性与购买入口状态 → 上架检查 → 产品工作区与待办 → 分摊辅助与草稿 → 真实结算和机构权限。每轮都验收新用户、已咨询用户、已购买用户三类路径。

## 6. 原则与验证边界

- KISS：产品介绍、服务套餐、商城商品分工明确，首轮不扩展更多可售类型。
- YAGNI：版本审批、统一交易平台及多机构后台等在需求与资源明确后推进。
- DRY：复用机构、商城库存、购买资格和接口状态，避免前端另建一套判断规则。
- SOLID：介绍负责展示、套餐负责售卖配置、履约负责服务执行、支付退款负责资金状态；页面组合这些能力，不混写业务规则。

本轮评估基于代码与已有操作反馈。自动化验证优先覆盖本次创建入口和历史类型回填；涉及支付、退款、下架及资格变更的生产操作，应使用明确测试订单验收。历史交付记录中的测试结论不能自动覆盖后续修改。
